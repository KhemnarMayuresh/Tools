# ChatGPT Splitter Improvements Implementation Plan

> **For agentic workers:** Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox syntax for tracking. This document plans the work; implementation is a separate request.

**Goal:** Make ChatGPT Splitter produce readable, size-bounded plain-text messages, with editable parts and a reliable sequential copy workflow.

**Architecture:** Preserve the existing static entry point and vanilla JavaScript structure. Extract a pure splitting/message module; keep source input, generated parts, user edits, and copy progress in explicit application state. Render user content through text nodes and textarea values, with all processing local to the browser.

**Tech Stack:** HTML, CSS, vanilla JavaScript, `Intl.Segmenter`, Clipboard API, Node's built-in test runner; Playwright for optional browser verification. No backend, framework, network tokenizer, or runtime CDN dependency.

**Spec:** `tools_analysis.md`, section 2, “ChatGPT Splitter — Improvements Needed.”

## Findings from the actual source

The tool already has three files: `ChatGPT Splitter/index.html`, `scripts.js`, and `styles.css`. It has no local README or tests.

- `scripts.js` builds messages containing literal `<br>` and `<pre>` strings, then copies those same strings with `navigator.clipboard.writeText`. HTML therefore appears in the clipboard instead of intentional plain-text line breaks.
- Generated content is assigned to `partDiv.innerHTML` with unescaped user input. Pasted markup can be interpreted as DOM content; fix this alongside clipboard correctness.
- Splitting uses `substring(start, end)` at fixed UTF-16 offsets. It can break words, Unicode surrogate pairs, paragraphs, and sentences.
- `charLimit` accepts a value through `parseInt` without explicit runtime validation. HTML min/max attributes do not protect a button-click handler from zero, negative, fractional, or nonnumeric values.
- The character limit applies only to raw payload. Added instructions and part markers make the copied message longer than the chosen limit.
- The initial instructions hardcode `1/10`, while generated messages use the actual number of parts. Acknowledgment wording varies, and the final message retains `[the task]`.
- Copy operations are neither awaited nor caught. There is no confirmed-success indicator, retry workflow, or clipboard fallback.
- The source counter uses `.length`; there are no per-part counters, editable parts, sequence tracking, or themes.

## Design decisions and global constraints

1. Scope is ChatGPT Splitter only. Preserve the existing Text-Compare implementation, analysis report, and earlier plan files.
2. Keep `ChatGPT Splitter/index.html` as the static entry point. Direct-file operation should work; restricted clipboard access must have a manual-copy fallback.
3. All input remains local. Store theme and optional profile preferences only; never automatically persist source text, edited parts, templates, or final-task instructions.
4. **Message limit means the complete copied message**, including wrappers and final instructions. Initial instructions must also fit. Default: 12,000 Unicode code points; accepted integer range: 50–1,000,000. Reject a limit that cannot accommodate the chosen instructions plus one payload grapheme.
5. Count Unicode code points; split only at grapheme boundaries. Use `Intl.Segmenter` for graphemes and sentence boundaries. If unavailable, show a compatibility message rather than silently corrupting characters.
6. Preserve source content exactly as read from the textarea: no trimming, dropped separators, duplicated text, or blank-line removal. Browser textarea newline normalization is part of this input representation.
7. Smart splitting chooses a paragraph boundary, then sentence boundary, then whitespace boundary, within the last 40% of the available payload budget. Otherwise use the last safe grapheme boundary within budget. A single grapheme exceeding the available budget produces a clear error.
8. The editable initial template supports only `{totalParts}`. Part wrappers are generated by the application. A separate Final task field defaults to “Please process the complete content according to my original request.” No unresolved `[the task]` or hardcoded total survives serialization.
9. Provider profiles are conveniences, not claims about context windows. Offer Manual, ChatGPT, Claude, Gemini, and Custom profile labels; start each at the conservative 12,000-character default until the user configures it. Display the selected character budget and allow overrides.
10. The report's GPT-3.5/GPT-4/Claude/Gemini token capacities are historical references. Do not convert a context-window number into a supposed web-app message limit. If shipping model-specific numeric profiles later, verify them against current official sources and label whether each value describes API context, input, or UI behavior.
11. Token display is an **approximate estimate**, initially `ceil(codePointCount / 4)`. Explain that language, code, and model tokenizer affect accuracy. It must not enforce character limits or promise model compatibility. Exact tokenizer integration is optional follow-up scope.
12. Proposed initial resource limits: 2 MiB UTF-8 source input and at most 1,000 parts. Validate before generating/rendering, show a useful error, and allow the user to increase the message limit. Render the first 25 part cards, with a Load more control.
13. Regeneration after edits requires an in-page confirmation explaining that edited parts will be replaced. Changes to source, limit, profile, template, or final task mark existing output stale and disable its copy controls until regenerated.

These are proposed defaults where the report does not specify behavior. They provide an unambiguous implementation contract without implying current provider limits.

## Review focus

- Pasted HTML, ampersands, and marker-like strings remain literal text in the preview and clipboard.
- Empty input, invalid limits, oversized instructions, and oversized individual graphemes produce clear states with no partial output.
- Hindi text, combining marks, emoji sequences, and long unbroken text reconstruct exactly after splitting.
- Part-number width changes at 9→10 and 99→100 must not make serialized messages exceed budget.
- Denied clipboard permission, edited parts, stale output, and asynchronous copy completion must not falsely advance or corrupt sequence progress.

## Shared interfaces and state

```text
Options = { messageLimit: number, locale: string, smartSplit: boolean,
            initialTemplate: string, finalTask: string }
Part = { id: string, payload: string, sourceStart: number, sourceEnd: number,
         edited: boolean }
Bundle = { initialMessage: string, parts: Part[], messages: string[],
           totalParts: number, sourceCodePoints: number }

countCodePoints(text: string) -> number
estimateTokens(text: string) -> number
validateOptions(options: Options) -> { valid: boolean, errors: string[] }
serializeInitial(template: string, totalParts: number) -> string
serializePart(payload: string, partNumber: number,
              totalParts: number, finalTask: string) -> string
buildBundle(source: string, options: Options) -> Bundle
```

`sourceStart`/`sourceEnd` are UTF-16 offsets into the original source, with end-exclusive semantics. They remain provenance when a part is edited; edited payloads need not concatenate to the original source. Validation errors prevent generation, not just copying.

Application state tracks source/options revision, generated revision, parts, initial-message edits, copied message IDs, next sequence position, and a generation ID for asynchronous clipboard results. Individual copying marks the corresponding message copied but does not move the sequential cursor. Part edits invalidate that message's copied status and move the cursor back to it if already passed.

## Task 1: Safe plain-text messages and validated limits

**Files:** `split-core.js`, `scripts.js`, `index.html`, `tests/split-core.test.cjs`.

**Interfaces:** Produce `countCodePoints`, `estimateTokens`, `validateOptions`, `serializeInitial`, and `serializePart` for Tasks 2–4.

- [ ] Write failing tests: `serializePart('<b>A & B</b>', 1, 2, '')` retains literal markup, has real newline delimiters, and contains actual `1/2` markers. Only the last part appends the completion instruction. The initial message substitutes `{totalParts}` and has no hardcoded `1/10`.
- [ ] Add limit tests for 0, -1, 49, fractional values, `NaN`, infinity, 1,000,001, and an oversized initial template. Require explicit validation errors; 50 and 1,000,000 are valid numeric limits, subject to message overhead.
- [ ] Run `node --test "ChatGPT Splitter/tests/split-core.test.cjs"`; confirm missing behavior fails.
- [ ] Implement plain-text serializers. Use newlines and fixed `[START PART i/n]` / `[END PART i/n]` markers. Treat any marker-like text inside the payload literally; do not parse it as application metadata.
- [ ] Replace unsafe `innerHTML` payload rendering with `textContent` or textarea `.value`. Copy serialized application-state strings, never DOM HTML.
- [ ] Add awaited clipboard success/error status and a readonly selected-text fallback. Test a literal `<img onerror=...>` payload in the browser; no image element or execution may appear.
- [ ] Run core tests and verify copied initial/part messages contain intentional plain-text instructions and unchanged payload.

## Task 2: Smart, Unicode-safe splitting within the full message budget

**Files:** `split-core.js`, `tests/split-core.test.cjs`.

**Interfaces:** Produce `buildBundle(source, options) -> Bundle`; consume Task 1 serializers and counters.

- [ ] Write failing tests for exact concatenation of part payloads, paragraph preference, sentence fallback, whitespace fallback, and a long unbroken word. Assert every copied message's code-point count is at most `messageLimit`.
- [ ] Add Unicode fixtures: Hindi with combining marks, decomposed accents, emoji with skin tone and zero-width joiner, and CRLF-normalized textarea input. Assert no part boundary splits a grapheme and no content is trimmed.
- [ ] Reserve wrapper/final-task overhead before selecting boundaries. Generate using a provisional total, then repeat with the actual total until numbering overhead stabilizes. Bound passes by part-count digit widths; fail clearly if limits cannot be satisfied. Do not split once and append unchecked wrappers afterward.
- [ ] Test 9→10 and 99→100 transitions, a long final task, an oversized grapheme, no paragraph boundaries, and one-message input. A single-message input still uses the same wrapper/final-task contract.
- [ ] Treat empty source as zero parts and no copy sequence. Whitespace-only source is legitimate content and must survive exactly. Preserve all separators with the preceding or following part, never discard them.
- [ ] Validate the 2 MiB source and 1,000-part caps before rendering any output. Add a representative large-input test demonstrating bounded completion without generating tens of thousands of cards.
- [ ] Run core tests; require passing content-preservation and full-message-budget assertions across all fixtures.

## Task 3: Editable parts, templates, profiles, and counters

**Files:** `index.html`, `scripts.js`, `styles.css`, browser tests.

**Interfaces:** Consume `Bundle` and pure serializers. Recalculate messages from current editable payloads rather than retaining stale serialized strings.

- [ ] Add source character count and labeled approximate token estimate. Show each part's payload count, full copied-message count, remaining budget, and approximate token estimate.
- [ ] Add editable payload textareas, editable initial template, and Final task field. Generate an editable initial-message card; editing it affects the actual copied initial message and its size validation.
- [ ] Add Manual/ChatGPT/Claude/Gemini/Custom profiles with visible adjustable character budgets. Keep provider labels separate from capacity claims; switching a profile restores its configured budget and marks output stale. Store each profile's configured numeric budget as a UI preference, never its text content.
- [ ] Validate edits live. An over-budget initial message or part keeps its content but disables copying that message and sequential progress at it; show how many characters exceed the limit. Do not silently truncate or repartition edited text.
- [ ] Track source/options changes as stale output. On an explicit Generate action, regenerate immediately if no output has been edited; otherwise use the in-page replace-edits confirmation. Cancelling retains existing edits while output stays visibly stale and uncopyable.
- [ ] Add browser checks proving edits appear verbatim in the copied message, counters include wrapper overhead, a profile change invalidates output, and regeneration cancellation preserves edited text.
- [ ] Render 25 cards initially. Sequence navigation must reveal its target card without eagerly creating every card. Clear All resets source, generated/edited content, progress, and pending copy revision safely.

## Task 4: Reliable “Copy Next” workflow

**Files:** `scripts.js`, `index.html`, browser tests.

**Interfaces:** Consume the current validated message strings and generation revision from Tasks 1–3.

- [ ] Define sequence order: initial instructions, Part 1 through Part N. Completion instructions are included in the final part; no separate “all sent” step is required.
- [ ] Implement Copy Next, per-card Copy, position indicator, copied badges, and Restart copy sequence. The primary button names its next target and becomes disabled at completion.
- [ ] Disable duplicate sequential copy requests while one is pending. Advance only after successful clipboard completion for the current generation; older promise results must not change newer state.
- [ ] On clipboard failure, show/select the current message for manual copying. Require an explicit “Mark this message copied” action to advance after the manual fallback. Merely showing the fallback is not a successful copy.
- [ ] When an already-copied part or initial message is edited, remove its badge and move sequential progress back to the earliest changed message. Preserve badges for unaffected messages. Restart resets badges and cursor but retains text edits.
- [ ] Add browser tests for success, rejection, duplicate clicks, Clear All during pending clipboard completion, per-card copy without cursor movement, edited-message reset, restart, and the last-part completion state.
- [ ] Verify the UI never claims that text was sent to an AI service. “Copied” reflects clipboard progress only; the user still pastes each message into their chosen app.

- [ ] Review the final diff for accidental changes to Text-Compare or other tools. Record any unmet acceptance criterion before declaring the implementation complete.

## Delivery order and acceptance

Tasks 1–2 are the first useful milestone: safe plain-text copy and content-preserving smart splits whose complete messages fit the limit. Tasks 3–4 add the editing and sequential transfer workflow. Task 5 completes the presentation and release checks.

Acceptance requires: no literal application-generated HTML in copied messages; pasted markup remains inert; unedited payloads reconstruct the original input; no grapheme is split; all copied messages respect the full-message limit; edits/counters stay synchronized; failed or stale copy operations never advance progress; no misleading model-capacity or exact-token claims; usable mobile/dark-mode layouts.
